# AerialKit - the ESP32 target: why it looks like this

This page is the *decision*: what the ESP32 port is allowed to depend on, and
where the boundary between AerialKit and the vendor stack sits. What the port
actually is - the IDF project, the arch layer, the board file, and the QEMU boot
that proves the same core runs on another instruction set - is
[17-esp32-port.md](17-esp32-port.md). What already exists for ESP32 flight
control elsewhere, and what this project takes from it, is
[22-esp32-survey.md](22-esp32-survey.md).

Where this stands: **the decision is made and the port exists; the board does
not.** No ESP32 hardware has been inventoried, and the Wi-Fi configuration M6
asks for is still compile-time.

## What is verified

```text
$ make port
port: xtensa-esp32-elf-gcc compiled 39 files for xtensa-esp-elf, 0 failed, 0 with warnings
port: riscv32-esp-elf-gcc compiled 39 files for riscv32-esp-elf, 0 failed, 0 with warnings
```

That is every file in `src/core`, `src/core/flight` and `src/core/sensors` -
the flight core, mixer, estimator, own math, parameters, console, blackbox,
alignment, calibration and the IMU driver - compiled with `-Wall -Wextra
-Wshadow -Wconversion -Wdouble-promotion -ffreestanding` for xtensa (ESP32,
ESP32-S3) and riscv32 (ESP32-C3, ESP32-C6, ESP32-P4). No MCU header, no libc,
no endianness or alignment assumption survived contact with a second
instruction set. `scripts/check-portable.sh` is the check, and it reports
warnings rather than hiding them, because nothing else in this project ever
compiles this code for those architectures.

What that does *not* mean: a portable core is not a flying aircraft. The arch
layer and the board file exist and the image boots under emulation
([17-esp32-port.md](17-esp32-port.md)), but no ESP32 hardware has been touched,
and the loop rate QEMU reports is a fact about QEMU.

## The toolchains

Both are aarch64-hosted, so this Pi builds them the same way it builds the
STM32 target. They live in the workspace's shared `toolchain/` directory next to
the ARM GCC:

| Directory | Compiler | Serves |
| --- | --- | --- |
| `xtensa-esp-elf` | `xtensa-esp32-elf-gcc` 14.2.0 | ESP32, ESP32-S2, ESP32-S3 |
| `riscv32-esp-elf` | `riscv32-esp-elf-gcc` 14.2.0 | ESP32-C3, ESP32-C6, ESP32-P4 |

They come from Espressif's crosstool-NG release `esp-14.2.0_20241119`, about
4 GB extracted. `make port` skips an architecture whose compiler is not there,
so a host without them still builds the STM32 target.

## The decision the port forces

The STM32 port is bare metal: our startup, our register layer, no vendor SDK.
The ESP32 is not the same shape of problem, and pretending otherwise would cost
more than it saves:

- **It does not start like a Cortex-M.** The ROM bootloader loads an *app
  image* with a header, a segment table and a checksum, and the flash cache has
  to be set up before anything runs from flash-mapped memory. A bare-metal
  start means writing that image format ourselves.
- **The reason this target exists is the radio.** The goal's ESP32 milestone is
  Wi-Fi configuration, telemetry and logging. That is a binary blob, a
  co-processor and a large vendor stack - not something to reimplement.

So the decision (recorded in [00-decisions.md](00-decisions.md) as #6): **the
ESP32 port uses ESP-IDF for the platform, and AerialKit for the aircraft.** The
flight core, mixer, estimator, parameters, console and blackbox stay exactly
what they are - the files that already compile for xtensa - and IDF provides
the things that are not ours to own: the boot chain, the image format, the
Wi-Fi stack, and FreeRTOS underneath. The port boundary is the one that already
exists, which is the point of having drawn it.

## What the port still needs

1. **A board with a name.** No ESP32 board has been inventoried, and the pin
   map, the sensor bus and the output pins all follow from which one it is.
   This is the one item that blocks everything else, and it is a question for
   the owner of the aircraft rather than for the code.
2. ~~Wi-Fi configuration that is not a rebuild.~~ **Done** (2026-09-16): the
   credentials are text parameters (`wifi_ssid`, `wifi_pass`, `wifi_ap_ssid`,
   `wifi_mode`), one of them a secret, so a field change is `set` and `save`
   rather than a build - and the aircraft can carry its own network as well as
   join one. [17-esp32-port.md](17-esp32-port.md) has the three modes and why
   the access point is never open.
3. ~~A partition table of its own.~~ **Done** (2026-09-16):
   `ports/esp32/partitions.csv` reserves a 704 KB `aerialkit` region for the
   blackbox, and the saved configuration lives in IDF's `nvs` - the same split
   the F405 has, in this chip's terms. The log is the same
   `src/core/ak_flashlog.c`; [17-esp32-port.md](17-esp32-port.md) has the table
   and the adapter that writes to it.
4. ~~Outputs.~~ **Done** (2026-09-16): the DShot generator is portable, and
   turning its edges into a waveform on a chip whose PWM peripherals are not
   timers-with-DMA is the ESP32's version of `arch/*/output.c` - the RMT, one
   channel per motor, with the servos on LEDC channels. [07-outputs.md](07-outputs.md)
   has the timing; the Arduino-style RMT reference in ArduPilot's ESP32 HAL is
   what the shape came from. **And it runs on the host since 2026-09-17**,
   against a modelled RMT and LEDC - which is how the check found that every
   frame this file sent was a quarter of a frame (`rmt_transmit()` takes bytes,
   not symbols). [07-outputs.md](07-outputs.md) has that too.
5. ~~The receiver, the GPS and the sensor buses.~~ **Done** (2026-09-16), and
   they were the *other* thing a pin map waits on: UART2 for the receiver,
   UART1 for the GPS, SPI for an IMU and I2C for a barometer, all four behind
   the same board contract the F405 implements. This is where the two chips
   differ in the aircraft's favour - SBUS is inverted and this one can invert
   its own receive line in the GPIO matrix, so it needs no transistor - and in
   the port's: the core's log read the flash a word at a time, which is free on
   memory-mapped flash and a transaction here, so the store grew a block read
   and a used log's resume stopped costing a boot. What is still missing is the
   same thing as always: a board, and something on the other end of each wire.
