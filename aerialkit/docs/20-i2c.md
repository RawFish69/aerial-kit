# AerialKit - the second sensor bus

I2C, because that is where the barometer is on the boards that have one:

```text
PB6 (SCL) ---+--- pull-ups ---+---   DPS310 / BMP280 / anything with a register map
PB7 (SDA) ---+----------------+
             I2C1, 400 kHz, address 0x77
```

The wing's own flight controller puts its barometer on I2C and so does almost
every AIO in this class - the SPI bus is spoken for by the gyro's bandwidth, and
a barometer needs about thirty bytes a second. That is the whole reason this
exists: not for elegance, but because the aircraft this firmware is meant to fly
has its height sensor on the other bus.

## The bus is a seam, so the driver never noticed

`ak_bus.h` was written for the IMU: a register number in, bytes out, plus a
delay, and nothing about pins or chip selects. A driver written against it runs
on either bus, and the proof is that **not one line of `ak_baro_dps310.c`
changed**. The board decides whether the barometer's bus is the SPI one or the
I2C one, and the driver finds out by asking for a register.

| | SPI (`ak_spi.c`) | I2C (`ak_i2c.c`) |
| --- | --- | --- |
| Who is addressed | a chip select pin, held low for the frame | a 7-bit address in the frame |
| Both directions | one transfer per half | a register, a repeated start, then the bytes |
| Pins | push-pull, the master drives both | **open drain**, many devices on two wires |
| Speed | APB1 / 8, tens of MHz | 100 or 400 kHz, set by CCR |

The pins are the difference that bites. I2C's SCL and SDA are pulled up by
resistors and every device on the bus can only pull them *down*; a push-pull
output would be two devices driving the same wire in opposite directions the
first time two of them spoke. `ak_pin_af_open_drain()` exists for that and for
nothing else.

## The three numbers the F4's I2C wants

This part is not the newer "TIMINGR" I2C. It wants the APB1 clock in whole MHz,
the SCL period in APB1 clocks, and the maximum rise time in clocks plus one -
and it wants them right, because there is no error flag for a bus running at the
wrong speed. Getting one wrong produces corrupted bytes or silence, which reads
exactly like a wiring problem.

The arithmetic is in `src/arch/stm32f405/i2c_timing.h`, away from any register,
and it is checked against RM0090 27.6.8-27.6.10 in `tests/test_i2c.c`:

| | Formula | 42 MHz APB1 | 16 MHz (HSI fallback) |
| --- | --- | --- | --- |
| FREQ | APB1 in MHz, clamped to 2..42 | 42 | 16 |
| CCR, standard mode | `fPCLK1 / (2 × fspeed)`, minimum 4 | 210 at 100 kHz | 80 |
| CCR, fast, Tlow = 2 Thigh | `fPCLK1 / (3 × fspeed)` | **35** at 400 kHz | 13 |
| CCR, fast, Tlow/Thigh = 16/9 | `fPCLK1 / (25 × fspeed)` | 4 - which is why nobody uses this duty at 400 kHz | 1 |
| TRISE, standard | `1000 ns × fPCLK1 + 1` | 43 | 17 |
| TRISE, fast | `300 ns × fPCLK1 + 1` | 13 | 5 |

The expected numbers were worked out from the manual rather than by running the
code and writing down what it said, which matters: a test that agrees with the
implementation is a test that agrees with its own bug.

## Where the NACK goes

An I2C read is two transactions and a repeated start: the register number is
written, then the address is sent again with the read bit. Where the master
stops acknowledging decides where the slave stops sending, and the manual gives
a different answer for each length - all three of which a barometer uses:

| Length | Sequence | What it is for |
| --- | --- | --- |
| 1 byte | clear ACK and set STOP, *then* read | a who-am-i |
| 2 bytes | clear ACK, **set POS**, wait for BTF, read both | a sixteen-bit coefficient |
| 3 or more | read until two remain, clear ACK, read the last two, STOP | pressure, temperature, acceleration |

POS is the part nobody guesses: with it clear, the acknowledge for a two-byte
read lands after the first byte and the master waits for a third that the slave
has already been told not to send. The failure is a timeout on a device that is
answering perfectly.

Every wait has a bound, and a bound that is reached resets the peripheral
(`SWRST`) rather than returning half a reading. A sensor that stops answering
must not be able to stop the aircraft.

## What is verified, and what is not

Verified on the host: the timing arithmetic above; the bit positions in
`tests/test_regs.c` - the enables, the flag bits, and the two mode bits at the
top of CCR; and, since 2026-09-16, **the transaction sequences themselves**,
against a modelled bus in `tests/host_i2c_model.c` that raises the flags as a
part would and answers as a sensor does - the one-byte read with its early
NACK, the two-byte read through POS and BTF, a longer read with the register
pointer walking, a write that ends on BTF, and an address nobody answers
followed by a transaction that still works
([21-port-on-the-host.md](21-port-on-the-host.md)).

What no model can say: **nothing here has been on a wire.** There is no
barometer on the bench board and no I2C device of any kind wired to it, so the
timing, the acknowledge's analogue half, clock stretching and a stuck bus are
all still the scope's. A model answers in the order the driver expects; a part
answers with an edge.

Three things a bench session needs to settle, in this order:

1. **The pull-ups.** Nothing here sets them; they are on the board or they are
   not, and without them the bus reads as permanently low.
2. **The address.** `AK_BOARD_BARO_ADDRESS` is 0x77, which is the DPS310 and
   the BMP280 with SDO strapped high. A part strapped the other way answers at
   0x76 and this line is the change.
3. **Fitting it.** `AK_BOARD_BARO_FITTED` is 0, so the bus is configured but
   not handed to the core: a board that says "no barometer" is more honest than
   one that spends a second probing a bus with nothing on it. Set it to 1 and
   the same driver that is tested against a fake bus starts talking to a real
   one.

There is no bus recovery for a slave that is holding SDA low. The usual cure is
to clock SCL by hand nine times with SDA released, and this firmware does not do
it - a stuck bus is reported, not treated. That is written here rather than
found at a bench.

## The other implementation: the same seam, a different peripheral

Everything above is the F405's I2C, and the *driver-facing* half of it is the
part that carried over to the wing's board: `ak_bus.h` did not change, the
DPS310 driver did not change, and the board file is the only file that knows
which of the two implementations is under it. What did not carry over is the
peripheral, which is the newer one with a single timing register
([25-at32-survey.md](25-at32-survey.md)), and the *sequences* are not the same
by a wider margin than the register names:

| | STM32F405 | AT32F435 |
| --- | --- | --- |
| How a transfer starts | `START` bit, then an address byte through the data register | **one write to ctrl2**: the address, the direction, the byte count and the start condition |
| Who performs the address phase | the driver, by sending a byte | the peripheral |
| Where the acknowledge is decided | the driver, and differently for one byte, two bytes and more (POS) | the count: every byte but the last, and the stop comes by itself |
| The end of a transfer | BTF, then a `STOP` bit | `stopf`, set when the count runs out and auto-stop is on |
| The data registers | one, read and write | `rxdt` to read, `txdt` to write |

So a second host model exists for it, `tests/host_i2c_model_at32.c`, and it does
the same job the F405's does: it answers as a device with a register file, and
the real driver runs its real sequences against it - a one-byte read, a
two-byte read, a burst, a write, an address nobody answers and the transfer
after it, a bus that was never enabled, and the count's two edges (nothing to
do, and more than the eight-bit count can hold, which is refused rather than
truncated).

**And it earned its keep on the first run.** The driver builds each transfer by
clearing the fields of ctrl2 a transfer owns and OR-ing its own values - and
the mask was written from the comment beside Artery's own `i2c_transmit_set()`
rather than from its value, so it covered the address, the direction and the
start bit and *not* the byte count. The second transfer then OR'd its count into
the first one's: a three-byte read, then a one-byte read, and the peripheral was
told to move three bytes and stopped the third waiting for a byte the slave was
never asked for. On a bench that is a barometer that answers the first time and
times out afterwards, which is the sort of thing that gets blamed on the
barometer. The mask is `0x03FF67FF` now, which is what the reference's is.

The same three bench questions above apply to this board, with two answers
already known: the pull-ups are the AIO's own, and the part is fitted - a DPS310
at 0x77 on I2C2 (PH2/PH3), so `AK_BOARD_BARO_FITTED` is 1 there. What is still
the scope's is whether the timing register lands on 400 kHz on that board's
traces and what a real DPS310 answers.

## And what happens when the bus stops answering

Every wait in both ports is bounded, and reaching the bound ends the transfer
properly - the stop condition, the flags cleared, the control register back to
what it was - rather than leaving a frame half-sent for the next start to be
read as a continuation of. That is the promise that keeps a dead barometer from
being a dead aircraft, and until 2026-09-18 **not one of those paths had ever
been executed**: the modelled buses always answered, and the only failure the
tests reached was an address nobody acknowledges - which both parts report with
a flag of their own rather than a wait that runs out.

So both models can now stop answering. `host_i2c_model_stall_after()` and
`host_i2c_at32_stall_after()` answer a chosen number of status *changes* and
then go quiet, and each port's test walks that number up: zero is a bus that
never comes up at all, and each step beyond it lets one more wait succeed before
the bus dies - the start, the address phase, the byte each part waits for, the
stop. Every point has to come back as an error rather than a hang, and has to
leave a bus that works when it answers again:

```text
  ok       a bus that answers 0 flags and stops is an error on a one-byte read, not a hang
  ok       and a two-byte read with 0 flags answered is an error or the right pair, never a wrong reading
  ok       and the bus works again after 0 flags
...
  ok       the sweep reached the sequence dying part-way, not only at once
```

Between them the two sweeps leave **no line of either `i2c.c` unreached** in
`make coverage`, which is the state both files are in now - the last port files
that were not. The two things that took the second pass are worth knowing for
the next file that gets this treatment: the sweep has to be **re-armed for every
transaction** (once a transfer fails at a given budget, every *later* transfer
on that bus fails at its first wait, so the two-byte and burst waits are never
reached), and the last two lines in the AT32's needed a failure a stall cannot
produce - a bus somebody else is holding, which `host_i2c_at32_bus_busy()` is
for. That one is the case `wait_idle()` exists for: the peripheral is fine and
the *bus* is not free, and the answer is to give up rather than wait.

Three things fell out of writing it, and each one is the kind that only a test
that *runs* the path can find:

- **Counting the driver's reads was the wrong unit.** A wait that times out
  polls the status register two hundred thousand times with the same byte in it,
  so the first draft's counter spent the whole budget on one bus that did not
  answer and left the *next*, healthy transaction reading zero for ever. The
  test next door caught it immediately - "and the bus still works afterwards"
  went red. An answer is a change the driver can see.
- **The AT32's model never cleared its start bit, and the hardware does.**
  `transfer_abort()` sets the stop bit on whatever ctrl2 holds, so on a model
  that left GENSTART sitting there the abort looked like *another start*: the
  model stayed mid-transfer with the bus busy, and the recovery read timed out.
  The F405's model had already learned the same thing about its own start bit
  ("leaving it set is what made the next control write look like another
  start"), which is the argument for the two models being read side by side.
- And a third, which is not a bug but was invisible: the F405 port can bring up
  **three** I²C controllers and the AT32 two, and the branch that enables the
  ones no board here uses had never run. It does now, because a port that can
  only bring up the bus its own board happens to use is a port that fails on the
  next board instead of here.
